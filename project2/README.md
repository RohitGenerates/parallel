# Project 2: Cache-Optimized Tiled Matrix Multiplication Engine (OpenMP & Loop-Interchange)

## Architectural Overview
This project is a **100% standalone, pure C/OpenMP** implementation of an advanced, cache-aware matrix multiplication engine ($C = A \times B$) designed for modern multi-core memory hierarchies. It achieves high arithmetic throughput and memory efficiency through:

1. **Loop Interchange ($i$-$k$-$j$ order)**: Replaces stride-$N$ column traversals in matrix $B$ with stride-1 contiguous row streaming, maximizing L1 cache line spatial locality.
2. **2D Cache Tiling / Blocking ($64 \times 64$)**: Decomposes large matrices into sub-blocks tailored to fit comfortably within the CPU's L1/L2 data cache ($32\text{ KB}/48\text{ KB}$ per core), eliminating cache thrashing and memory bus bottlenecks.
3. **OpenMP Multi-Core Parallelization**: Parallelizes 2D block traversal with `#pragma omp parallel for collapse(2) schedule(dynamic, 16)` and inner vectorization via `#pragma omp simd`.
4. **Modular C Driver (`Matrix2D`)**: Clean memory lifecycle management, numerical verification, and a built-in automated benchmark suite written in native C.

All benchmarking, timing with `omp_get_wtime()`, metric calculations (GFLOPS, Speedup, Efficiency), ASCII table formatting, and CSV/TXT reports are generated directly inside the C program with zero external runtime dependencies.

## Build & Execution Instructions

### Option 1: Automated C Benchmark Suite (Recommended)

#### Using Make:
```bash
cd project2
make all
make run
```

#### Manual Compilation with GCC:
```bash
cd project2
gcc -O3 -Wall -Wextra -static -fopenmp src/matrix_engine.c src/main.c -o bin/matmul_engine -lm
./bin/matmul_engine --benchmark
```

* **What it does**:
  1. Runs pre-flight correctness verification comparing sequential against OpenMP tiled ($N=500$, threads=4).
  2. Executes 1 warmup run + 3 measured repetitions across matrix dimensions ($500 \times 500$, $1000 \times 1000$, $2000 \times 2000$) and OpenMP thread counts ($2, 4, 8$).
  3. Measures wall-clock time with `omp_get_wtime()`.
  4. Computes Mean runtime, Min runtime, Standard Deviation, Speedup ($S_p = T_{seq}/T_{par}$), Parallel Efficiency ($E_p = \frac{S_p}{p} \times 100\%$), and Throughput (GFLOPS).
  5. Renders formatted ASCII summary tables to `stdout`.
  6. Exports results to `benchmark/results/project2_results.csv` and `benchmark/results/project2_results.txt`.

---

### Option 2: Standalone Single-Configuration Executables

You can run individual experiments using custom flags:

```bash
# Compare Sequential vs OpenMP Tiled on 1000x1000 with 4 threads and block size 64:
./bin/matmul_engine -n 1000 -t 4 -b 64 -k both

# Run only the OpenMP Tiled kernel on 2000x2000 with 8 threads:
./bin/matmul_engine -n 2000 -t 8 -b 64 -k omp_tiled

# Run verification mode (checks exact numerical equivalence):
./bin/matmul_engine -n 500 -t 4 -b 64 -v
```

#### Supported CLI Flags:
* `-B`, `--benchmark` : Run complete automated benchmark suite
* `-n <size>`         : Matrix dimension $N \times N$ (Default: `1000`)
* `-t <threads>`      : Number of OpenMP worker threads (Default: `4`)
* `-b <tile_size>`    : Dimension of L1/L2 cache block tile (Default: `64`)
* `-k <kernel>`       : Kernel to execute: `seq` | `omp_tiled` | `both` (Default: `both`)
* `-v`, `--verify`    : Verify numerical correctness between sequential and OpenMP tiled

## Performance Metrics & Formulas

### 1. Arithmetic Throughput (GFLOPS)
For dense square matrix multiplication ($N \times N$), total operations are $2N^3$ floating-point ops ($N^3$ multiplications $+ N^3$ additions):
$$\text{GFLOPS} = \frac{2 \times N^3}{\text{Execution Time (seconds)} \times 10^9}$$

### 2. Speedup ($S_p$)
$$S_p = \frac{T_{\text{sequential}}}{T_{\text{parallel}}(p)}$$

### 3. Parallel Efficiency ($E_p$)
$$E_p = \left( \frac{S_p}{p} \right) \times 100\%$$

## Micro-Architectural Insights
* **Cache Line Reuse (Spatial Locality)**: In standard $i$-$j$-$k$ multiplication, iterating along the column index of matrix $B$ incurs stride-$N$ memory jumps, causing cache line underutilization. The $i$-$k$-$j$ order accesses rows of $B$ sequentially, ensuring all 8 doubles loaded in a 64-byte cache line are consumed.
* **L1/L2 Cache Tiling (Temporal Locality)**: Sub-dividing matrices into $64 \times 64$ blocks ($64 \times 64 \times 8 \text{ bytes} = 32\text{ KB}$) ensures the active sub-matrices fit within per-core L1/L2 cache capacity, drastically reducing main memory DRAM bus traffic and enabling substantial throughput scaling.
